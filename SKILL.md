# gost-docx

Работает с `.docx` по правилам из `references/gost-rules.md` и подключаемыми методичками пользователя. Не изменяет содержание пользователя и не придумывает факты, выводы, источники или персональные данные.

## Профиль документа

В начале определить профиль: отчёт по ГОСТ 7.32, курсовая, ВКР, лабораторная или практическая работа, отчёт о НИР, технический отчёт или пользовательский профиль на основе методички.

Профиль определяет структурные элементы и правила методички. Если методичка не предоставлена, использовать ГОСТ 7.32 как базовый профиль и сообщить об этом.

Если правила ГОСТ и методички расходятся, один раз в начале показать конфликт, указать оба источника и спросить, какой вариант сохранить для текущего документа. Не решать конфликт молча.

## Выбор режима

Сразу в начале определить режим. Доступны три варианта:

1. Аудит существующего файла: только чтение, отчёт в .md.
2. Форматирование копии по ГОСТ: исходный файл не трогается, результат `Имя_gost.docx`.
3. Создание нового .docx с нуля: сначала спрашиваются данные (см. ниже).

Если пользователь уже назвал режим, переспрашивать не нужно.

## Режим 1. Аудит

Запуск:

    python3 <путь-к-скиллу>/scripts/gost_docx.py audit файл.docx --out отчёт.md

`<путь-к-скиллу>` — каталог, в котором находится этот `SKILL.md`. Если агент уже
работает из каталога скилла, можно использовать `python3 scripts/gost_docx.py ...`.

Скрипт не меняет файл. Коды возврата: 0 — нарушений нет, 1 — есть ошибки (предупреждения не влияют), 2 — файл не открыт. Проверяются: формат A4, поля 30/15/20/20 мм, нижний колонтитул с PAGE по центру, отступ 1,25 см, интервал 1,5, нулевые интервалы до и после, выравнивание по ширине, Times New Roman 14 пт, точка в конце заголовка, формат подписей «Рисунок N – Название», порядок ссылок в квадратных скобках, местоимения первого лица, символ «•».

Не проверяются: номера страниц в содержании, поля в таблицах, нумерация разделов, формулы. Их нужно смотреть глазами после рендера.

## Режим 2. Форматирование копии

Исходный файл не перезаписывается. Работа идёт над копией `_gost.docx`. Перед запуском спросить, какие пункты из списка конфликтов применять (см. ниже). Затем проверить результат режимом 1 и провалидировать `scripts/office/validate.py` из базового скилла `docx`.

Запуск:

    python3 <путь-к-скиллу>/scripts/gost_docx.py format файл.docx

Результат: `файл_gost.docx` рядом с исходным. Исходный файл не меняется. Скрипт выравнивает поля и размер страницы, добавляет колонтитул с PAGE по центру, задаёт стиль Normal и оформляет абзацы основного текста. Заголовки, подписи, таблицы и титул не трогает, поэтому после прогона нужно смотреть аудитом: ошибки по содержанию (порядок ссылок, местоимения, маркеры) остаются.

## Режим 3. Создание

Сначала спросить только данные, необходимые выбранному профилю. Личные данные для титульного листа не запрашивать: при создании использовать страницу-заглушку:

    ТИТУЛЬНЫЙ ЛИСТ

Страница входит в общую нумерацию, но видимый номер на ней отсутствует. Если в существующем документе титульный лист уже есть, сохранить его и не заменять заглушкой.

- главы и подразделы (если не заданы, предложить базовую структуру ГОСТ 7.32);
- реферат, ключевые слова и другие структурные блоки, если они нужны профилю;
- список источников (если не задан, оставить пустой шаблон, не выдумывать).

Текст глав, выводов и источников в этом режиме не придумывать. Запуск:

    python3 <путь-к-скиллу>/scripts/gost_docx.py build задание.json файл.docx

Формат `задание.json`: `profile`, `abstract`, `keywords`, `introduction`, `chapters` (массив объектов `{heading, paragraphs}`), `conclusion`, `sources`, `appendices`. Все содержательные значения пишет пользователь. Структурные элементы и разделы основной части начинаются с новой страницы. Содержание создаётся автоматическим полем Word, которое можно обновить через контекстное меню. Создание выполняется через npm `docx` версии 9.15.3, установленной локально в `scripts/`.

## Конфликты: спрашивать, не решать молча

Если методичка и ГОСТ расходятся, спросить пользователя. Шаблон вопроса:

    Конфликт: [что именно]. Методичка: [вариант А]. ГОСТ 7.32 (пункт N): [вариант Б].
    Какой применить?

Открытые вопросы из `gost-rules.md`: аннотация или реферат; заголовки разделов; правила титульного листа пользовательской методички; нумерация отсылок; Courier New и кнопки; листинги как рисунки; лимит объёма.

Уже решено пользователем: для новых документов использовать титульную страницу-заглушку без личных данных; заголовки разделов по ГОСТ 7.32, 6.2.3; библиографические описания по ГОСТ Р 7.0.100-2018. Профиль может переопределить набор структурных элементов.

## Окружение

- Python 3 с lxml. Для рендера и проверки внешнего вида: LibreOffice (`soffice`, путь `/opt/homebrew/bin/soffice`), PDF переводится в картинки через PyMuPDF (`fitz`). `pdftoppm` в системе нет.
- Node: `scripts/` содержит локальный `docx@9.15.3`. Глобальной установки не требуется.
- Для дополнительной проверки Word-файла можно использовать валидатор базового
  скилла `docx`, если он установлен конкретным агентом. Путь к нему нужно
  получить из документации этого агента; отсутствие базового скилла не мешает
  запуску аудита и форматирования.
- Для аудита и форматирования нужен Python 3 с `lxml`, для создания — Node.js
  18+ и зависимости из `scripts/package-lock.json`. Команды установки зависят
  от среды агента и описаны в `docs/installation.md`.
