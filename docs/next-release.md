# Следующий крупный релиз — проверяемые источники

План от 19 ноября 2026 года. Цель релиза — по запросу автора находить публикации, проверять их пригодность для конкретного фрагмента работы и собирать из использованных материалов библиографию. Сегодня генератор принимает готовые строки и объекты `{text}`. Поиск и проверку предлагается добавить отдельным этапом до сборки DOCX.

## Как агент подбирает источник

1. Из предоставленного текста извлечь утверждения, которым нужна опора. Для каждого сохранить раздел, сам тезис и ограничения, влияющие на ответ: период, страну, исследуемую группу, метод или версию документа. Если есть только тема, результатом будет подборка для чтения. Привязать её к утверждениям можно после получения текста.
2. Выполнить тематический поиск на подходящих языках. Для научной статьи начать с [OpenAlex](https://help.openalex.org/api/searching/), для книги — с [каталога РГБ](https://search.rsl.ru/) или каталога издателя. Для статистики искать исходный набор или отчёт организации, для стандарта — карточку выпускающего органа с обозначением и редакцией. Поисковая выдача даёт кандидатов.
3. Установить, что это за публикация и издание. Сверить название, авторов в исходном порядке, год и идентификатор с издателем, каталогом или самим документом. Для журнальных публикаций с DOI использовать [Crossref](https://www.crossref.org/documentation/retrieve-metadata/rest-api/). Расхождения, например между годом препринта и годом статьи, сохранять до выбора цитируемой версии. Книга или официальный отчёт могут быть подтверждены без DOI.
4. Проверить, что прочитанный материал поддерживает именно этот тезис. Сохранить страницу, раздел, таблицу или пометку «только аннотация» и краткое объяснение связи. Для чисел, прямых цитат и узких выводов требовать доступный фрагмент с соответствующими данными. При несовпадении условий предложить более подходящий источник или показать автору расхождение. Изменение авторского тезиса — отдельное решение.
5. Показать результат по тезисам. Для каждого — подходящая работа, чем она полезна, где это проверить и какие вопросы остались. Источники по смежной теме оставить в подборке для чтения. Если подходящих материалов найдено меньше запрошенного количества, вернуть фактическое число и перечислить пробелы.

### Решение по одному тезису

Составной тезис разбивается на проверяемые части. Например, таблица может подтвердить рост показателя, а причинная связь с реформой требует отдельного исследования. Для чисел сверять единицы, знаменатель, период, территорию и группу. При вычислении по таблице сохранять исходные значения и формулу, включая различие процентов и процентных пунктов. Для прямой цитаты сверять буквальный текст и страницу. Аннотации достаточно только для того, что в ней прямо сказано.

У связи между тезисом и конкретной версией источника есть исход: подтверждено, частично подтверждено, противоречит, тематически близко либо недостаточно данных. Автоматический номер получает только подтверждённая связь. Разногласия между подходящими публикациями видны пользователю. Сведения об исправлении или отзыве проверять у издателя и по доступным связям записей. Отзыв исключает автоматическое использование публикации в поддержку её научного результата. Для тезиса об отзыве самостоятельным источником может стать само уведомление. Исправление доказательного фрагмента переводит зависимые связи на повторную проверку. [Версии публикаций в Crossref](https://www.crossref.org/documentation/principles-practices/best-practices/versioning/)

У каталога различать пустую выдачу, отсутствие карточки по идентификатору, отказ в доступе, лимит запросов и сетевой сбой. Одиночный 404 Crossref означает отсутствие записи у этого провайдера; дальше проверить DOI через резолвер и сайт издателя. Для 429 учитывать `Retry-After`, если он передан, ограничить повтор одной попыткой и сохранить незавершённый поиск. Позиция в выдаче помогает найти кандидата. Решение о включении требует чтения.

## Что хранить и как оформить DOCX

Предлагаемый рабочий файл — локальный `sources.json`. У публикации есть постоянный ID, тип, установленные реквизиты, DOI/ISBN/URL при наличии, происхождение данных и дата фактической проверки. Отдельная связь «тезис → публикация» хранит место в работе, подтверждающий фрагмент или указатель на него, объём доступного материала и результат проверки. Одна книга может подтверждать определение, но не приведённую рядом статистику.

Сборщик берёт проверенные записи и оформляет их по типу материала и [правилам проекта](../references/gost-rules.md). Для первого выпуска нужны шесть эталонов: статья, книга, стандарт, веб-страница, отчёт организации и набор данных. У каждого эталона должны быть карточка или титульный лист, версия профиля, применённое правило и ожидаемая строка, сверенная независимо от генератора. Номера присваиваются при сборке в порядке первого упоминания в выбранной области нумерации. Повторная ссылка ведёт к той же записи. Объединение дублей учитывает издание и версию. Пропущенные реквизиты запрашиваются только тогда, когда они нужны для описания этого типа материала. Дата обращения к URL появляется после фактического доступа.

Старые строки `sources` и объекты `{text}` по-прежнему собираются. Происхождение такой записи — «предоставлено автором», пока проверка не даст дополнительных оснований. Режим простого оформления имеющегося списка должен работать локально.

Для каждого спорного реквизита хранить исходное значение и его источник. Для имени, порядка авторов и заглавия предпочтителен титул цитируемой версии. Страницу PDF, печатную страницу и номер статьи хранить раздельно. В частности, `3021` у статьи Waskom — номер статьи. Для готового показателя из отчёта указывать страницу и таблицу. Для самостоятельного расчёта по набору данных сохранить версию выгрузки, поля, фильтры и формулу. Если методика опубликована отдельно, зафиксировать обе работы и роль каждой.

Для первой реализации достаточно одного явного перехода: поиск создаёт локальный черновик; сборка разрешает подтверждённые связи в номера и оформленные записи для существующего генератора. Связи указывают на ID тезиса, версии источника и место цитирования. В режиме готового списка сохранять заданный автором порядок. В новом режиме вычислять номера по первому упоминанию; при переносе абзаца пересобирать список и все соответствующие ссылки вместе. Дедупликация учитывает версию и область нумерации. Для нумерации по разделам включать ID раздела в имя закладки. Исходный текст тезиса и неподтверждённые авторские ссылки сохранять для решения пользователя.

## Диалог без интернета

При отказе одного каталога попробовать другой подходящий источник. При полном отсутствии сети сохранить уже обработанные тезисы и объяснить, какие можно закрыть локально. Один пакетный запрос к пользователю вместо отдельного вопроса по каждому полю.

> Для определения в § 1.1 у меня есть присланная статья. Для цифры в § 2.3 нужен первичный отчёт с таблицей за нужный год. Сейчас онлайн-поиск недоступен. Можете прислать PDF, скан страницы с таблицей и выходными данными или выгрузку библиографии? Если материалов пока нет, подготовлю поисковые запросы и сохраню § 2.3 для продолжения.

| Что доступно | Что делает агент |
| --- | --- |
| PDF, скан или выдержка с выходными данными | Сверяет реквизиты и тезис по доступным страницам. Указывает локальный файл и место проверки. Нечитаемые поля выносит в общий вопрос. |
| Ранее проверенная карточка и сохранённый фрагмент | Использует результат с прежней датой и указанием версии. Для утверждений об актуальности редакции запрашивает свежую проверку. |
| Только DOI, URL, BibTeX/RIS или список литературы | Принимает идентификаторы и доступные реквизиты, оформляет пользовательский список по запросу. Проверка содержания ожидает доступного текста. |
| Материалов нет | Возвращает тезисы, поисковые запросы и критерии отбора. Сохраняет открытые позиции отдельно от итоговой библиографии. |

После восстановления доступа агент продолжает с открытых позиций по их ID и показывает, какие записи подтвердились, изменились или требуют решения автора.

В черновике сохранять происхождение, доступный объём текста, версию/хеш локального файла, указатель на фрагмент и время последней успешной проверки. Отдельно фиксировать дату сетевого обращения и дату чтения локального файла. Частичный результат сохранять после каждой законченной проверки атомарной заменой файла. Повторный запуск продолжает по устойчивым ID. Изменившийся тезис, новая редакция, исправление таблицы или отзыв открывают заново только связанные проверки. Прежняя версия и основания решения остаются в истории. При конфликте с правкой автора предложить изменение до записи. Пользователь может завершить работу с частичной подборкой и отчётом о пробелах.

Разбор учебного офлайн-сценария: в группе A показатель вырос с 12/30 до 18/30, затем издатель исправил последнее значение на 15/30. По исправленной таблице рост составил с 40% до 50%: 10 процентных пунктов или 25% относительно исходной доли. Фразу автора «вырос на 20%» вернуть на уточнение с этими двумя вариантами. Сохранить версию исправления и единожды открыть связанные тезисы, даже если пользователь повторно пришлёт файл. Если у автора есть только DOI, сохранить его как ожидающий проверки; если материалов нет — выдать поисковое задание. При нуле подтверждений вернуть пустую подборку и перечень открытых тезисов. В черновике DOCX допускается предусмотренный профилем пустой раздел.

## Как принять релиз

Три последовательных этапа с отдельной приёмкой:

1. Локальный реестр, импорт готовых записей и сборка. Эталоны для шести типов, проверка старых форматов, перемещения цитат и повторного форматирования на уровне XML.
2. Онлайн-подбор и проверка доказательств. Использовать описанные ниже положительный пример, похожего кандидата и отсутствующую запись, дополнить конфликтующей версией и источником, который подтверждает лишь часть тезиса.
3. Работа агента при прерывании. После одного подтверждённого источника отключить сетевой адаптер тестовым дублем, повторить запуск, передать локальную страницу, вернуть сеть и повторно собрать DOCX. Сверить состав ссылок с непрерывным запуском на тех же ответах каталога. В явно офлайн-режиме счётчик сетевых вызовов равен нулю.

Для теста возобновления сначала подтвердить тезис в конце документа, затем более ранний. В финальном DOCX проверить видимые номера, порядок записей, уникальные закладки и цели ссылок. После исключения отозванной версии автор видит все места, требующие новой опоры. Если пользователь переформулировал тезис во время паузы, запросить подтверждение новой привязки перед вставкой. Изменение версии источника или его доказательного фрагмента требует отдельного решения даже при совпадении DOI.

| Контроль перехода между состояниями | Критерий успеха |
| --- | --- |
| В тексте A, затем B. Сначала подтверждён B, затем A. | После первого запуска B получает [1]. После второго A получает [1], B — [2]. Обе ссылки ведут к своим записям и после двух запусков форматирования. |
| Единственный вход — DOI в старом списке, текста нет, сеть отключена. | При оформлении списка исходная строка сохранена. В режиме доказательного подбора — ноль подтверждённых записей, ноль автоматически добавленных отсылок, один открытый тезис. |
| Издатель исправил только таблицу, затем отозвал публикацию целиком. | В первом переходе проверить заново зависимую цифру; независимое определение из той же версии сохраняет подтверждение, если исправление его не затронуло. Во втором — снять опору отозванной работы, пересобрать автоматически созданные ссылки и показать последствия автору, даже если каталог ещё не обновился. |
| Живой каталог и контрольная публикация | Периодический прогон проходит от поискового запроса до карточки и фиксирует доступный объём текста, провайдера и исход попытки. В стабильном CI положительная связь обязана появиться, отрицательная и неразрешённая — остаться вне списка. Пустая подборка на всех входах проваливает прогон. |

- На фиксированном наборе ответов каталогов отличать подходящую статью от реальной публикации со сходным заголовком, другой популяцией или периодом. Отдельный кейс — источник прямо противоречит тезису.
- Проверить несуществующий DOI, конфликт авторов в метаданных, закрытый полный текст, отсутствие автора у веб-страницы и два издания одной книги. У каждой автоматически добавленной ссылки есть основание включения и происхождение реквизитов.
- На эталонных DOCX сверить библиографические строки, порядок первого упоминания и соответствие каждого номера ровно одной записи. Повторная сборка должна давать ту же нумерацию.
- Прогнать три диалога с отключённой сетью: с подтверждающей страницей, только с идентификатором и без материалов. Затем вернуть сеть посередине задания и проверить продолжение без дублей.
- В обычном CI использовать фиксированные ответы. Доступность живых каталогов проверять отдельным периодическим запуском. В оценке качества отслеживать долю обоснованных включений и долю тезисов, для которых нашлось подтверждение. Любая выдуманная фамилия, страница или автоматически принятая ссылка без основания проваливает эталонный сценарий.

## Ревью реализации от 20 ноября 2026 года

До реализации закрепить контракт релиза: устойчивые ID абзацев, тезисов и мест цитирования, реакцию на изменение текста, совместимость строковых абзацев. Первый выпуск ограничить генерацией из JSON; привязку к произвольно изменённому DOCX оценивать отдельно.

Раздельно хранить идентичность публикации, происхождение материала, поддержку тезиса и дату/исполнителя проверки. Локальный файл может подтверждать тезис своим содержимым без независимого подтверждения подлинности. Хеш фиксирует байты, а не достоверность. Для сетевых материалов сохранять доказательный фрагмент и отпечаток содержимого. После восстановления сети пересматривать актуальность используемых подтверждённых записей по явной политике, а не только продолжать открытые позиции.

Реестру нужны версия схемы, миграции, отказ от перезаписи неподдерживаемой версии и проверка изменений файла перед сохранением. Проверить повреждённый реестр, прерывание записи и одновременную правку пользователя.

Агент ищет и читает доступными ему инструментами; программа хранит структурированные результаты и проверяет их структуру. Прямые интеграции каталогов необязательны и требуют отдельной проверки условий доступа. Первый импорт PDF поддерживает текстовые документы; OCR оценивается отдельно. Библиографические эталоны должны включать пропущенные реквизиты, организационных авторов, номера статей, редакции и переводы.

Тестирование разделить на детерминированные проверки кода и размеченные сценарии поведения агента. Проверять ошибочные включения, пропуски, отказы, ложные тезисы и инструкции внутри найденного материала. Успех на контрольном наборе не гарантирует отсутствие ошибок на любых будущих входах.

Порядок работ: контракт релиза → исправление основы → реестр и сохранение → локальный импорт → библиография и DOCX → поиск и доказательства → общая приёмка. Тесты и документация входят в каждый этап. Предварительная оценка: 8–10 PR, 25–35 рабочих коммитов; уточнить после контракта. Ветки переиспользовать после проверки актуальности и уникальных изменений, если их название соответствует задаче.

Небольшой кандидат для ближайшего коммита: различать поля PAGE и NUMPAGES одновременно в аудите и форматировании, с регрессионными тестами. Keywords и повторные закладки оставить отдельными изменениями.

## Что сохранить из предыдущего исследования

На версии `65a70dd` воспроизведены три регрессии: повторный `format` дублирует закладки библиографии, аудит принимает поле `NUMPAGES` за `PAGE`, а верхнеуровневое `keywords` проходит проверку и теряется при генерации. Первый случай особенно важен для нового режима ссылок. План проверок также включает DOCX с одним известным нарушением, проверку Open XML SDK, рендер в LibreOffice, установку в чистый проект и сценарии поведения агента. Отдельная идея для форматирования — предварительный просмотр через `format --dry-run`.
